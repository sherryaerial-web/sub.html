# Sherry Aerial Studio 請假代課系統 v2.1

GitHub Pages 前端搭配 Google Apps Script、Google Sheets 與 Omcean Booking API。老師與管理員使用同一個網站，登入角色會決定可見功能。

## 系統入口

- `index.html`：GitHub Pages 前端，老師登入後可請假、領取代課及查看個人紀錄。
- `vvip.html`：公開 VVIP 優先選課意願頁面。會員從啟用中的 OB 名稱選擇自己，不需登入老師系統。
- `Code.gs`：完整 Apps Script 後端。
- 管理員以管理員帳號登入同一個前端後，可開啟邀請、OB 待辦、異動申請、核對與 VVIP 選課後台。
- 正式網址：`https://sherryaerial-web.github.io/sub.html/`

## PWA 與即時通知

網站可安裝到手機主畫面與電腦桌面，但不建立離線快取；每次打開仍讀取當下的正式課程、代課與管理資料，避免顯示過期待辦。`OneSignalSDKWorker.js` 只負責接收通知，不攔截或快取網頁請求。

上線即時通知前，先在 OneSignal 建立 Web app，網站網址使用正式網址，Service Worker 檔案設為 `OneSignalSDKWorker.js`。關閉 OneSignal 自動詢問通知權限；本系統只會在使用者登入後按下「開啟通知」時請求系統權限。

到 Apps Script「專案設定 → 指令碼屬性」設定：

| 屬性 | 用途 |
|---|---|
| `ONESIGNAL_APP_ID` | OneSignal Web app 的 App ID，前端只會取得這個公開 ID。 |
| `ONESIGNAL_REST_API_KEY` | OneSignal REST API Key，只能存在 GAS 指令碼屬性，不得放進前端、Git 或對話。 |
| `PUSH_EXTERNAL_ID_SALT` | 不需手動填寫；前兩項完整後，後端會在第一次設定通知身分時自動產生。 |

未設定 OneSignal 時，通知入口會安全隱藏，不影響原有功能。設定完成後，可收到新代課邀請、領課成功、退出核准／駁回與關課結果。第一輪 22:30 關課後仍只缺一人的課程，系統會在「關課管理」顯示可編輯、一鍵複製的社群文字；第二輪 23:40 完成或失敗也會通知課程管理員。

- iPhone／iPad 需使用 iOS/iPadOS 16.4 以上，先用 Safari 「加入主畫面」，再從主畫面圖示開啟並登入。
- Android 與支援的桌面瀏覽器可安裝網站後，由系統內的「開啟通知」進行設定。
- 若曾選擇不允許，必須到手機或瀏覽器的網站通知設定重新開啟。
- 通知不會新增通知工作表，也不會改動正式 Sheet 欄位；通知設定、去重與社群文字只保存在 Script Properties。

## 試算表契約

部署前先建立試算表副本備份。既有欄位不移動，新欄位只追加在右側。

### CourseList

`CourseList` 是最近一次手動同步的 OB 課表快照。A:D 保持原位置。

| 欄 | 標題 |
|---|---|
| A | 日期 |
| B | 時間 |
| C | 課程 |
| D | 指導者 |
| E | OB Calendar ID |
| F | OB Class ID |
| G | OB 老師 ID |
| H | 是否代課 |
| I | 最後同步時間 |

API 同步不會覆蓋請假、代課或異動歷史。同步失敗時會保留原本快照。

### 請假代課紀錄

首次執行 `ensureSystemStructure_()` 時，舊「工作表1」會更名為「請假代課紀錄」。若新舊兩張表同時存在，程式會停止，必須先人工確認哪張才是正式資料。

`ensureSystemStructure_()` 可安全重複執行，屬於冪等設定／遷移：既有代課編號與 OB Calendar ID 不會被覆蓋，只有可證明為唯一完全相符的缺漏資料才會補值；內容沒有變化時也不會重複寫入遷移 audit。首次 OB 同步完成後必須再執行一次，讓舊資料能使用新取得的 Calendar ID 做安全 backfill。

### 一般代課延後開始

- 老師只能在右側「調整課程或時間」選擇原時段、延後 15 分鐘或延後 30 分鐘；左側直接認領固定使用原時段。
- 一般課以 60 分鐘計算，只有課名包含精確字串「綢吊」時為 90 分鐘；「舞綢」仍是 60 分鐘。課後一律保留 15 分鐘換場。
- 若延後占用下一堂待領代課，系統會把下一堂標記為「延後占用／待管理員關閉 OB」，不填代課老師，也不算第二堂代課。此占用標記不直接參與薪資；薪資仍依 OB 最終開課成果與人數計算。
- 管理員在 OB 調整原堂開始時間並關閉被占用堂後，回管理頁依序按「同步 OB 課表」與「重新核對 OB」。原堂時間相符、被占用堂 Calendar ID 已消失後才會完成核對。

正式啟用此功能前，必須先備份正式「請假代課紀錄」。將新版程式推到 Apps Script HEAD 後、更新正式 deployment 前，手動執行一次 `setupSystemStructure()`，並讀回確認 Z:AB 依序為「實際開始時間、延後分鐘數、延後占用來源代課編號」。不得清空、整張覆寫或搬移既有 A:Y 資料。

### OB 取消待領代課

- 找不到代課老師的普通課程可先直接在 OB 取消；程式部署本身不會自動寫入正式 Sheet。
- 管理員回到管理頁按「同步 OB 課表」後，系統只會把下個月、仍為待領取、尚無代課老師，而且目前連結的 OB Calendar ID 已消失的課程列入「OB 已取消」。老師端與待邀請清單不再顯示這些課程。
- 管理員在「OB 已取消」頁籤勾選課程後按「關閉勾選課程」。後端會先驗證整批，再依代課 UUID 更新明確列；任一堂狀態已變或 OB 課程仍存在時，整批不寫入。
- 對應的 VVIP 選課會保留紀錄並標示「課程已取消」，且不再占用三堂額度，會員可補選其他課程。
- 此流程不處理已有人領取、特別課群組、非下個月或沒有 OB Calendar ID 的舊資料；這些狀況仍需在原本的管理工作區個別處理。

### 結束本輪代課邀請

- 管理員可在「邀請中」頁籤按「結束本輪邀請」，一次關閉所有目前仍為開放中的邀請；已領取、請假與 OB 核對資料完全不變。
- 老師端重新整理後顯示「本輪代課領取已結束」，不能再送出普通代課或特別課領取。
- 未來重新對老師開放邀請時，該老師會直接進入新一輪並恢復可領取，不需調整全域暫停設定。

### 其他工作表

`ensureSystemStructure_()` 會建立或檢查：

- `代課邀請`：隱藏邀請權限與查看狀態。
- `操作紀錄`：取消、退出、核對與管理操作歷史。
- `系統設定`：包含「暫停全部領取」。
- `登入帳號`：只保存 Salt、PIN 雜湊、在職狀態、角色、登入保護與可教授類別。
- `VVIP選課紀錄`：VVIP 的 Email、月份、OB Calendar ID、原課程快照、確認／取消狀態與操作者。此表只由 VVIP 公開 API 與管理員後台使用。
- `VVIP名單`：OB 名稱與 Email 的私密對照；公開頁只取得 ID 與名稱，不會取得 Email。
- `VVIP選課設定`：`activeMonth`、`isOpen`、`openedAt`、`closedAt` 等本期開放設定。
- `薪項設定`：老師專屬時薪、出席人數階梯、固定加給與固定扣項。首次建立時會安全帶入既有薪資表的 19 筆規則，已有資料時不覆蓋。
- `薪資來源資料`：補充 OB `calendar` API 沒有提供的課程收入、盈利等月報欄位。
- `薪資同步快照`、`薪資明細`、`薪資結算`：保存每次同步版本、逐堂計算與發布／確認狀態。
- `薪資異議`、`薪資付款設定`：保存老師問題、管理員回覆與付款備註。
- `自主練習系列`、`自主練習場次`：保存每週循環規則與逐日產生的自主練習，所有紀錄均使用獨立 UUID。
- `自主練習參與者`：保存建立者、參與者及每位老師各自的開始與結束時間。
- `自主練習例外`、`自主練習操作紀錄`：保存單次取消／衝突跳過與完整異動紀錄，避免循環場次被錯誤重建。

自主練習工作表與正式 `CourseList`、請假代課及薪資資料完全分離；初始化只建立缺少的工作表與空白欄位，不清空或覆寫既有人工資料。

正式啟用自主練習後，可在 Apps Script「觸發條件」建立每 10 分鐘執行一次的 `runScheduledPracticeReconciliation`。此函式會即時向 OB 讀取未來 45 天課表：OB 無法確認時整批不寫入；候補課程消失後才補入自主練習；正式課程復活時會取消衝突的自主練習並通知參與老師。部署程式本身不會自動新增正式觸發條件。

`ensureSystemStructure_()`、首次管理員初始化及密碼匯入都會將整張 `登入帳號` 設為保護範圍，只保留 Apps Script 實際執行帳號的編輯權，並關閉網域編輯。部署前必須另外確認整份試算表只分享給必要管理員；老師只使用 Web App，不可取得試算表檢視或編輯權。可到「資料 → 保護工作表與範圍」確認保護名稱為「系統保護：登入帳號」。

登入姓名選單直接讀取 `登入帳號`：姓名、Salt、PIN 雜湊完整且「是否在職」為啟用的帳號都會顯示。`老師名單` 已不再是登入必要資料，可保留為隱藏的舊資料表。

### VVIP 優先選課

VVIP 頁面只收集選課意願，**不代表正式保留 OB 名額**。同一位 VVIP 在當期最多可累積三堂不同的 `OB Calendar ID`；重複送出既有課程不會重複計算。會員若選錯，請聯絡管理員取消，會員端不提供自行取消。

管理員先在 `VVIP名單` 或管理頁建立 OB 名稱與 Email 對照。公開頁只顯示啟用中的 OB 名稱，Email 留在後端；所有選課仍維持「待人工確認」，正式保留名額前由管理員人工核對。

每期作業順序：

1. 先以管理員帳號在 `index.html` 按「同步 OB 課表」，確認下個月的 `CourseList` 都有 `OB Calendar ID`。
2. 在管理後台「VVIP 選課」頁籤建立或啟用 VVIP 名單，再按「開放本期選課」。如果下個月沒有課或有缺少 Calendar ID 的課程，系統會拒絕開放。
3. 將 GitHub Pages 的 `vvip.html` 網址傳給 VVIP。頁面會依日期顯示下個月全部有效課程，會員選擇自己的 OB 名稱後可分次累積最多三堂。
4. 在「VVIP 選課」頁籤依 Email 查詢、確認 Email、取消單堂或依課程查看登記會員；匯出 CSV 只包含有效選課，並已防護公式注入字元。
5. 截止時按「關閉本期選課」。關閉後會員不能再查詢或送出，管理員仍可查看與取消當期資料。

不要將 `VVIP選課紀錄` 分享給老師或 VVIP。公開頁不會取得其他會員 Email，也不會把 Email 放進網址。

## 薪資月結

OB `calendar` API 可提供課程、完整指導者、容量與出席人數，但不提供每堂實收與盈利。一般課可直接依 API 出席人數計薪；課名包含「特別課」時，必須在 `薪資來源資料` 補上該堂課程收入，否則整個版本保持草稿且禁止發布。盈利可留空，不影響老師應領薪資，但管理報表會顯示尚未補齊。

每月作業順序：

1. 在 `薪資來源資料` 貼上當月 OB 月報需要保留的收入／盈利欄位；有 `OB Calendar ID` 時優先填入，沒有時系統以日期時間與課名配對。
2. 薪資管理員在管理頁選月份，按「同步並試算」。每次同步建立新版本，不覆蓋舊資料。
3. 確認錯誤數為 0、抽查特別課與固定加扣後按「發布薪資」。草稿對老師完全不可見。
4. 老師在「我的薪資」逐堂核對後確認；有問題可指定明細提出異議，管理員回覆後保留完整紀錄。

特別課單一老師為課程收入 60%；課名含「特別課」且指導者為 `Sherry❤雪莉` 加一位合作老師時，雪莉列入應領 60%、合作老師 40%。獎金以鐘點費小計計算：15,000（含）至未滿 20,000 為 3%，20,000（含）至未滿 30,000 為 4%，30,000（含）以上為 5%；固定加扣不納入獎金基礎。

## 37 位老師密碼一次性匯入

來源檔為 `老師密碼表.xlsx`，工作表名稱是 `密碼表`，A1:B1 必須是「老師、密碼」，A2:B38 共 37 位老師。PIN 必須是 4 位數字；開頭為 0 的 PIN 必須保留為四碼文字。

請嚴格依照下列順序：

1. 先完成 `ensureSystemStructure_()`，並先建立第一位管理員帳號。
2. 在正式 Google 試算表選擇「檔案 → 匯入 → 上傳」，上傳 `老師密碼表.xlsx`。
3. 匯入位置選「插入新工作表」，不可取代目前試算表，也不可覆蓋其他資料。
4. 確認工作表仍叫 `密碼表`，A1 是「老師」、B1 是「密碼」，A2:B38 恰好 37 筆。
5. 確認 37 個登入姓名無重複，並與 OB 的顯示姓名完全一致。姓名中的空格、符號與表情符號不要自行改寫。
6. 在 Apps Script 編輯器的函式選單選擇 `importTeacherAccountsFromPasswordSheet`，手動執行一次並授權。
7. 成功結果應顯示 `imported: 37`。新帳號會設為「在職＝是、角色＝老師」；既有同名帳號只更新 Salt 與 PIN 雜湊，原本的角色、在職狀態、登入保護與可教授類別全部保留。因此第一位管理員即使也在 37 人名單內，仍會保持管理員權限。
8. 到 `登入帳號` 確認每位老師都有 Salt 與 PIN 雜湊，且表內沒有任何原始四碼 PIN。
9. 回到 `密碼表`，確認 A2:A38 姓名仍保留、B2:B38 已清空；來源工作表不會被刪除。
10. 到 `登入帳號` H 欄「可教授類別」補資料。新帳號的此欄會保持空白，既有帳號則保留原值；之後可用「、」分隔多個類別。

正式啟用「自己的正課可安排特別課」時，將 `蜜莉 戴` 視為 Emily，並只在她的 `登入帳號` H 欄既有值中追加 `舞綢`；不得覆蓋原有類別，也不得修改同列其他欄位。

匯入函式會先驗證完整 37 筆，再依序寫入完整帳號批次、清除來源 PIN、設定完成標記。三個範圍都會事先保存快照；任一步驟失敗時，系統會補償還原 `登入帳號`、`密碼表` PIN 與原完成標記。若回復本身失敗，錯誤訊息會明確列出未成功回復的資料。只有三步全部成功才回報完成，並以指令碼屬性 `TEACHER_PASSWORD_IMPORT_COMPLETED_AT` 防止誤執行第二次。

此函式沒有前端或 Web API 路由，只能由有權限的管理員在 Apps Script 編輯器手動執行。不要將 `老師密碼表.xlsx`、PIN、Salt 或雜湊提交到 GitHub。

## 第一位管理員

`登入帳號` 尚無任何帳號時，先到 Apps Script「專案設定 → 指令碼屬性」暫存：

| 屬性 | 值 |
|---|---|
| `INITIAL_ADMIN_NAME` | 管理員姓名 |
| `INITIAL_ADMIN_PIN` | 管理員四碼 PIN |

手動執行 `initializeFirstAdminFromProperties` 一次。成功或失敗後，兩個暫存屬性都會立即刪除。必須在匯入 37 位老師前完成，因為已有帳號後不能再使用首次管理員初始化。

## 完整部署順序

1. 建立正式 Google 試算表完整副本，記錄副本名稱與建立時間；同時記錄目前可用的 Apps Script 版本號、Web App deployment ID，以及正式前端 Git commit。三者必須視為同一組可回復版本。
2. 開啟綁定該試算表的 Apps Script，將 repository 的 `Code.gs` 完整覆蓋舊程式並儲存。
3. 在「指令碼屬性」設定 `OMCEAN_API_TOKEN`。請使用重新產生的新 token，不要沿用曾貼在對話或程式碼中的 token。
4. 依「PWA 與即時通知」設定 `ONESIGNAL_APP_ID` 與 `ONESIGNAL_REST_API_KEY`；金鑰不可貼入對話或提交到 Git。
5. 手動執行 `setupSystemStructure()` 一次，完成工作表改名、欄位追加與輔助工作表建立。
6. 若同時看到「工作表1」與「請假代課紀錄」，立即停止，不要刪資料；先人工比對並只保留正確正式表。
7. 依上一節建立第一位管理員。
8. 依「37 位老師密碼一次性匯入」流程建立老師帳號。
9. 確認 `登入帳號` 內所有應登入者都有完整 Salt、PIN 雜湊且「是否在職」為啟用，並在 H 欄補上可教授類別、I 欄補上功能權限。正式設定為冠蓉／IVY：`course_admin、payroll_admin、vvip_admin`；Sherry：不設定管理權限；Tako：`course_admin、vvip_admin`。未補類別前，跨道具領取判斷不完整。
10. 到 Apps Script 左側「觸發條件」刪除舊版 `syncCourseListFromApi` 的時間觸發條件。新版只允許管理員手動同步。
11. 部署 Apps Script Web App 的新版本；執行身分使用部署者，存取權沿用目前正式設定。
12. 若 Web App URL 改變，更新 `index.html` 內的 `APP_URL`。
13. 先以管理員登入並按「同步 OB 課表」，確認同步範圍為今天至下個月底，且 `CourseList` 筆數、日期及 OB Calendar ID 都合理。
14. 首次同步成功後，再次手動執行 `setupSystemStructure()`，檢查回傳的 migration 計數 `assignedIds`、`linked`、`manualReview`。確認唯一完全相符的舊資料已安全連結，無法唯一判定者留在「待人工核對」。此步驟可安全重複執行，不會覆蓋既有 ID。
15. 完成同步後 backfill，再用測試帳號測 Web App：登入、選日期、送出一堂測試請假、取消測試資料，最後檢查管理員後台。
16. 將 `index.html`、`vvip.html`、`manifest.webmanifest`、`OneSignalSDKWorker.js` 與圖示一起發布到 GitHub Pages，等待 Pages 完成後再開正式網址測試桌機與手機。
17. 各以一個老師與管理員帳號登入已安裝的 PWA，手動開啟通知，再送出一則可辨識的測試代課邀請，確認只有目標老師與有對應權限的管理員收到。
18. 以兩個老師帳號同時嘗試同一堂代課，確認只有第一位成功；再檢查邀請、改課、退出與 OB 核對流程。

## 必測情境

1. 老師登入後先選日期，再看自己的課程；「全選日期」與「清除全部」正確。
2. 大量請假分批送出，前端只有在後端回報精確成功筆數後才顯示成功。
3. 未受邀老師看不到代課；受邀老師看到全部待領代課，但看不到邀請順序或其他受邀者。
4. 自己請假的課不會出現在可領清單。
5. 跨類代課必須選擇改課方式並填寫備註；同類也能選填難度與備註。
6. 同時領取同一堂課，只能有一位成功。
7. 未被領取的請假可自行取消；已領取或已處理 OB 的項目只能提出取消申請。
8. 代課老師退出必須填原因，由管理員核准後重新開放。
9. OB 同步遇到零筆、無效 JSON、HTTP 錯誤或任一無效課程時，原本 `CourseList` 不會被清空。
10. 管理後台依帳號權限顯示代課、薪資與 VVIP 工作區；全域暫停領取與重新核對皆可操作。
11. 薪資草稿不會出現在老師頁；發布後老師只能看到自己，確認與異議狀態可正確更新。

## 回復方式

前端、GAS 與試算表資料契約必須以相容組合一起回復，不可只回復其中一層。

1. 立即停止老師操作與 OB 同步，記錄故障時間；另存故障期間新增的請假／代課資料，供回復後人工補登。
2. 找出部署前記錄的「前端 Git commit、Apps Script 版本號／deployment ID、試算表副本」。不要憑「上一版」猜測。
3. 若舊 GAS 仍使用舊表名「工作表1」，必須先還原部署前試算表副本，再啟用舊 GAS。禁止讓舊 GAS 直接讀取已改名為「請假代課紀錄」的 v2.1 試算表。
4. 在 Apps Script「部署 → 管理部署作業」以記錄的舊版本建立或切回部署，確認 Web App URL 對應該版本。
5. 將 GitHub Pages 回復到與該 GAS 版本配對的前端 commit；不要混用新版前端與舊 GAS。
6. 回復後依序做 smoke check：老師登入成功、能讀取既有請假紀錄、送出一堂標記清楚的測試請假並確認試算表確實新增，再刪除／取消該測試資料。
7. 管理員登入後確認管理頁權限；若舊版沒有管理頁，至少確認舊版預期的管理操作與工作表讀寫正常。
8. 核對故障期間另存的資料並人工補登，確認無遺漏後才重新開放老師使用。

若只有 API 異常、不需要版本回復，先使用管理端「暫停全部領取」，保留現有 `CourseList`，確認 token 與 OB 回應後再手動同步。

## 本機驗證

```bash
node --check tests/backend-core.test.js
node --test --test-name-pattern='VVIP' tests/backend-core.test.js
node --test --test-name-pattern='VVIP' tests/vvip-frontend.test.js
node tests/vvip-visual-check.mjs
```

整個網站準備正式上線前，才依使用者確認執行完整系統測試與完整視覺檢查；日常開發只執行本次功能相關的測試。

視覺測試會執行一條桌機與一條手機 viewport journey，在 15 個畫面節點各自截圖，共產生 30 個視覺狀態／截圖；另有 VVIP 桌機與手機各一張。它檢查非空白、水平溢出、控制項裁切及手機導覽遮擋。送出、權限、鎖定、取消／退出、邀請、薪資及核對等行為由 `backend-core.test.js` 與 `frontend-contract.test.js` 的單元／契約測試覆蓋。GAS 語法檢查可將 `Code.gs` 複製成暫存 `.js` 後執行 `node --check`；正式檔案仍以 `Code.gs` 為準。
