# Sherry Aerial Studio 前台、VVIP 與薪資整合設計規格

## 目標

在既有請假代課系統上完成三項整合更新：

1. 重整老師與管理員前台外觀，移除不合適的方形品牌圖示，建立有高級感但仍適合日常工作的介面。
2. 將 VVIP 公開選課改為後台白名單制，會員只選自己的 OB 名稱，不再自行輸入 Email。
3. 新增可由 OB API 手動同步、試算、發布、確認與提出異議的薪資模組。

明日優先選課上線所需的 VVIP 流程不得依賴薪資模組完成後才可使用。兩者共用登入與管理權限，但資料與發布狀態彼此隔離。

## 方案比較與決策

### 方案 A：整合既有 GAS、Google Sheet 與同一前端（採用）

延用目前的 Apps Script、正式試算表與 GitHub Pages。新增工作表、API action、功能權限與前端頁面，不另建登入系統。

優點是老師只需記一個網址與同一組姓名／末四碼，VVIP 與薪資可共用 OB 課程快照及管理操作紀錄，部署與維護成本最低。風險是 `Code.gs` 與 `index.html` 會繼續變大，因此新增邏輯必須以獨立函式區塊、明確資料契約及聚焦測試維持可讀性。

### 方案 B：薪資使用獨立 GAS 與試算表（不採用）

薪資資料隔離較強，但會重複登入、帳號、權限、OB 同步與部署設定。老師需在兩套系統間切換，管理員也需維護兩份名單。

### 方案 C：改用外部資料庫與完整後端（不採用）

擴充性最好，但超出目前明日開放 VVIP 與既有 Sheets 工作習慣的需求，會增加主機、身分驗證、資料遷移與維運負擔。

## 視覺設計

採用「A：藝廊編輯感」，不使用目前的方形風圖示，也不硬放不相干的空中藝術照片。

- 品牌以 `Sherry Aerial Studio` 文字字標為主，品牌標題使用優雅襯線字，操作介面使用清楚的無襯線字。
- 主色為墨黑、柔和白與深綠；暖金只用於細線與摘要，莓紅只用於待處理、錯誤與主要動作。
- 不使用漸層、裝飾性圓球或大面積單色卡片。狀態靠文字、數字與少量色彩共同表達。
- 次要文字使用足夠深的灰色，不能以低對比灰字代表停用。沒有資料時明確顯示「目前無待辦」或「本月尚未發布」。
- 若需要品牌視覺資產，使用專門製作的空中絲綢材質近拍窄幅圖，不使用其他教室或無關人物照片；沒有適合素材時以純文字品牌完成，不為了填版硬放圖片。

### 角色版型

- IVY、雪莉：桌機顯示完整管理工作台；手機首頁以單欄待辦呈現課程、代課、薪資與 VVIP。
- Tako：使用同樣的管理工作台結構，但只顯示課程／請假代課管理，不顯示薪資與 VVIP。
- 一般老師：簡潔首頁，只顯示自己的請假、代課、薪資與紀錄入口。
- VVIP：獨立公開頁，沿用簡潔的藝廊編輯風格。

手機管理首頁不得使用 2×2 小卡塞入多段文字。每項功能使用單欄列，右側顯示待辦數量；完整表格只在點入模組後顯示。桌機可使用較寬的多欄工作台。

## 功能權限

`登入帳號` 既有 A:H 欄位不得移動。右側追加「功能權限」欄，以逗號分隔的固定代碼保存：

- `course_admin`：課程、請假代課、OB 同步與核對。
- `payroll_admin`：薪資同步、試算、調整、發布與異議處理。
- `vvip_admin`：VVIP 名單、開關、登記與取消。

正式權限：

| 使用者 | 課程／代課 | 薪資 | VVIP |
|---|---:|---:|---:|
| IVY | 是 | 是 | 是 |
| Sherry❤雪莉 | 是 | 是 | 否 |
| Tako | 是 | 否 | 否 |
| 其他老師 | 否 | 僅本人 | 否 |

後端每一個管理 action 都必須重新驗證功能權限，不能只靠前端隱藏按鈕。

## VVIP 白名單

### 工作表

新增 `VVIP名單`：

| 欄 | 標題 | 用途 |
|---|---|---|
| A | VVIP ID | 後端建立的穩定識別碼 |
| B | OB 名稱 | 公開選單顯示名稱 |
| C | Email | 後端保存，不回傳公開頁 |
| D | 是否啟用 | 是／否 |
| E | 備註 | 管理員選填 |
| F | 建立時間 | 操作紀錄 |
| G | 更新時間 | 操作紀錄 |
| H | 更新者 | 管理員姓名 |

既有 `VVIP選課紀錄` 欄位不得移動，在右側追加 `VVIP ID` 與 `OB 名稱`。既有 Email 紀錄保留；新登記由後端依 VVIP ID 取得 Email 並寫入快照。

### 公開流程

1. 管理員先在後台維護 VVIP OB 名稱、Email 與啟用狀態。
2. 管理員同步下個月 OB 課程，再手動開放本期 VVIP。
3. 公開頁只取得啟用中的 `VVIP ID` 與 OB 名稱；Email 不回傳瀏覽器。
4. 會員以可搜尋選單選擇自己的 OB 名稱，再查看下個月全部課程。
5. 同一 VVIP 當期可分次累積最多四堂不同課程。重複送出既有課程不重複計數。
6. 選錯時由會員聯絡管理員，管理員在後台取消。

啟用中的 OB 名稱必須唯一；若重複，系統拒絕開放並要求管理員修正，不以完整或遮罩 Email 暴露身分。

此流程維持低摩擦，不使用 Email OTP 或會員密碼，因此公開頁會顯示啟用中的 OB 名稱，且知道他人名稱的人仍可能代為登記。新登記維持「待人工確認」，管理員核對後才視為有效意願。

## 薪資資料結構

### `薪項設定`

由現有 Excel `薪項表` 匯入並延用以下欄位：老師姓名、課程關鍵字、計費類型、人數門檻、金額。老師專屬且符合課程關鍵字的規則優先於預設人數階梯。

### `薪資同步快照`

保存每次計薪使用的 OB 原始欄位：月份、OB Calendar ID、課程日期時間、課程名稱、全部指導者及 ID、出席人數、容量、課程收入、OB 原始鐘點費、教室、分店、同步時間與資料版本。

API 回傳後先完整驗證，再一次寫入當月草稿快照。零筆、缺少 Calendar ID、課程名稱、指導者、出席人數或收入時，不覆蓋舊快照並列出錯誤。同步為管理員手動操作，不設定自動觸發。

### `薪資明細`

每一筆老師實際薪資一列，包含月份、明細 ID、Calendar ID、老師、日期時間、課程、計費類型、出席人數、課程收入、套用規則、比例或單價、薪資金額、是否人工調整、調整理由、版本與建立時間。

合作特別課同一個 Calendar ID 會產生雪莉與合作老師兩筆明細，兩筆分潤加總必須等於該堂課程收入。

### `薪資結算`

每位老師每月一列：鐘點費小計、獎金比例、獎金金額、固定津貼／扣項、應領總薪資、盈利、發布版本、確認狀態、確認時間與最後更新時間。

### `薪資異議`

保存異議 ID、月份、老師、明細 ID、問題說明、狀態、管理員回覆、提出時間、處理者與處理時間。異議處理完成後，老師必須重新確認薪資。

### `薪資付款設定`

保存老師、轉帳群組／銀行與備註，供管理員產生與既有「給雪莉的格式」相同的付款摘要。此表不提供老師端讀取。

## 薪資計算規則

計算採以下優先順序：

1. 課程名稱包含「場地租借」：鐘點費為 0。
2. 課程名稱包含完整字串「特別課」：套用特別課規則，不再讀取或維護人工貼上的 `特別課` 分頁。
3. 其他課程先找老師姓名＋課程關鍵字的專屬薪項，再找老師姓名的通用薪項，最後套用預設人數階梯。
4. 固定加給、固定扣項與固定月薪於逐堂鐘點費加總後加入。
5. 依鐘點費小計計算獎金，再得到應領總薪資。

### 一般特別課

- 課名含「特別課」且只有一位指導者：該老師（包含雪莉本人）取得課程收入 60%，四捨五入至整數。
- 若有多位非雪莉指導者且無法唯一判定分配，標記待人工處理並禁止發布，不自行平均。

### 雪莉合作特別課

- 課名含「特別課」，全部指導者包含 `Sherry❤雪莉`，且另有一位合作老師：雪莉取得課程收入 60%，合作老師取得 40%，兩者均四捨五入至整數。
- 因分別四捨五入造成 1 元差額時，以「合作老師＝四捨五入收入×40%；雪莉＝課程收入－合作老師」確保合計完全相符。
- 雪莉 60% 與合作老師 40% 都列入各自鐘點費小計並參與獎金計算。
- 若同堂有雪莉及兩位以上合作老師，標記待人工處理並禁止發布。

### 獎金

| 當月鐘點費小計 | 獎金比例 |
|---|---:|
| 未滿 15,000 | 0% |
| 15,000（含）至未滿 20,000 | 3% |
| 20,000（含）至未滿 30,000 | 4% |
| 30,000（含）以上 | 5% |

獎金金額為鐘點費小計乘以比例後四捨五入至整數。固定加給、扣項與固定月薪不納入獎金門檻。

未找到人數階梯、未知計費類型、缺少收入、缺少出席人數或找不到老師薪項時，不得猜測金額；該筆進入待人工處理，整月薪資在問題排除前不可發布。

## 薪資操作流程

1. 具 `payroll_admin` 權限者選擇月份，按「同步並試算」。
2. 後端抓取該月 OB 全部課程，驗證後建立不可變的同步快照及草稿明細。
3. 管理後台顯示總額、逐堂明細、套用規則與所有異常。草稿期間老師看不到薪資。
4. 管理員可對單筆薪資做人工調整，但必須填理由並留下操作紀錄。
5. 所有異常排除後，管理員按「發布薪資」。系統建立發布版本並鎖定該版本。
6. 老師登入後只看到自己的總額與逐堂明細。正確時按「確認無誤」；有問題時選擇明細並填寫原因。
7. 管理員處理異議並建立新版本後，原確認失效，老師重新確認。
8. 解鎖、重算、調整、發布、確認與異議處理全部寫入 `操作紀錄`。

## 錯誤與併發控制

- 同步、試算、發布、人工調整與老師確認使用 `LockService`，避免同時操作造成重複或部分寫入。
- 所有批次寫入先在記憶體完成驗證，再一次寫入；錯誤時保留上一個完整版本。
- 已發布月份不得直接被新同步覆蓋。管理員必須明確建立修正版，舊版本保留供稽核。
- 前端只在後端回傳精確成功狀態與版本號後顯示完成，不使用 `no-cors` 假成功。
- 薪資、Email、PIN、Salt、雜湊與功能權限不得出現在公開 API、前端常數或 GitHub。

## 測試與上線

開發中只跑本次改動相關測試，不重複執行完整審查。

聚焦測試至少包含：

- VVIP 白名單新增、停用、名稱唯一、Email 不公開、累積四堂與管理員取消。
- 三種功能權限與所有管理 API 的後端拒絕測試。
- 一般課薪項優先順序、場地租借、一般特別課 60%、雪莉合作 6：4、四捨五入與合計核對。
- 獎金門檻 14,999、15,000、19,999、20,000、29,999、30,000。
- 同步缺欄位、零筆、API 錯誤、未知薪項與已發布版本保護。
- 老師只讀本人薪資、確認、提出異議及修正版重新確認。
- 老師、Tako、IVY／雪莉、VVIP 的手機與桌機關鍵畫面；灰字對比、文字裁切、水平溢出與導覽遮擋。

正式上線前只執行一次完整後端、前端、秘密掃描與桌機／手機視覺驗證。VVIP 可在薪資模組仍維持草稿或關閉狀態時先獨立開放。
