# OB 購課與綠界電子發票整合設計

日期：2026-09-26  
狀態：待使用者審核  
實作位置：既有 Sherry Aerial 教室管理工作台（GitHub Pages 前端、Google Apps Script 後端、Google Sheets 資料儲存）

## 1. 目標

將 Omcean Booking（OB）的已付款轉帳購課訂單同步至既有管理工作台，讓授權管理員先核對資料，再由工作台呼叫綠界 B2C 電子發票 API 開立發票。

第一版的核心原則：

- 同步不等於開票；每日排程及手動同步都只建立待開立資料。
- 正式開票一定由管理員確認觸發。
- 支援兩個獨立綠界帳號／統編，由管理員人工切換。
- 防止重複同步、重複開票及多人同時操作造成的競態。
- 不自動處理退款作廢或折讓；只建立待處理提醒與人工結果紀錄。

## 2. 範圍

### 2.1 第一版包含

- 購買時間自 2026-09-26 00:00（Asia/Taipei）起的 OB 購課資料。
- 付款狀態為已付款，且付款方式為銀行轉帳的訂單。
- 個人 B2C 發票。
- 有買方統編及公司抬頭的 B2C 發票，由管理員人工補資料後逐筆開立。
- 同一付款參考編號內的多張課卡合併為一張發票、多個商品明細。
- 每日 00:00 自動同步一次，以及管理員手動立即同步。
- 兩組綠界商店設定、人工切換、分開流水號與操作稽核。
- OB 退款狀態偵測及人工處理追蹤。

### 2.2 第一版不包含

- 尚未付款的訂單。
- 非轉帳付款；目前現金與信用卡皆不納入。
- 2026-09-26 00:00 前的歷史訂單回補。
- 自動開票。
- 自動作廢、折讓或退款。
- 消費者載具蒐集與儲存。
- 從工作台寄送自訂發票信件；發票通知使用綠界寄至 OB Email 的既有機制。
- B2B 電子發票流程。

## 3. 權限

新增獨立的發票管理權限，第一版只授予 Ivy 與 Tako。

兩位管理員皆可：

- 查看發票管理頁。
- 執行手動同步。
- 切換預設開票帳號。
- 修改待開立資料。
- 逐筆開立發票。
- 批次開立符合條件的個人發票。
- 標記退款人工處理結果。
- 查看操作紀錄。

所有具狀態變更的操作都記錄操作者、時間、動作、目標唯一鍵、變更前後摘要與結果。

## 4. 系統架構

### 4.1 前端

在既有教室管理工作台新增「發票管理」入口，沿用現有登入與權限檢查，不建立第二套登入系統。

頁面分為：

1. 待開立
2. 資料異常
3. 已開立
4. 退款待處理
5. 操作紀錄

頁面上方固定顯示目前預設開票帳號、切換按鈕、上次同步時間及「立即同步 OB」按鈕。

### 4.2 GAS 後端元件

- `OB 購課同步器`：分頁讀取 OB 購課資料、套用篩選條件、補查單筆資料及付款參考編號。
- `發票資料服務`：正規化訂單、依付款參考編號分組、驗證欄位、建立待開立資料及狀態轉換。
- `綠界介接器`：依指定發票帳號組裝、簽署及送出開票請求，解析綠界結果。
- `帳號設定服務`：讀取目前預設帳號、個別待開立資料的預計帳號，以及兩組商店設定。
- `排程服務`：管理每日 00:00 的同步觸發器。
- `稽核服務`：以追加方式記錄同步、修改、切換帳號、開票與退款處理。

各元件維持單一職責；OB 回傳資料、內部發票資料及綠界請求資料使用明確轉換層，不直接相互耦合。

### 4.3 機密資料

兩組綠界設定分別包含 MerchantID、HashKey、HashIV，僅儲存在 GAS Script Properties。前端回應、試算表、日誌及錯誤訊息不得包含 HashKey 或 HashIV。

OB Token 沿用現有安全儲存方式，不新增至前端或試算表。

## 5. 資料模型與 Sheets 安全

發票資料使用獨立工作表，不混入既有人工維護欄位。建議分為：

- `InvoiceQueue`：一列一張預計發票，保存內部狀態、OB 唯一鍵、付款參考編號、買方資料、金額、預計開票帳號及綠界結果摘要。
- `InvoiceItems`：一列一個商品明細，以內部發票 ID 關聯 `InvoiceQueue`。
- `InvoiceAudit`：只追加的操作紀錄。
- `InvoiceSettings`：非機密顯示設定與目前預設帳號；綠界金鑰不寫入此表。

所有更新使用明確唯一鍵定位單列，不使用整張清空、整表覆蓋或依畫面列號猜測資料。寫入前後均檢查唯一鍵及目前狀態；不符合預期狀態時停止並回報。

## 6. OB 同步規則

一筆購課資料必須同時符合以下條件才可進入待開立流程：

1. `purchasedAt` 換算 Asia/Taipei 後不早於 2026-09-26 00:00。
2. `paymentStatus` 為已付款。
3. `paymentMethod` 為銀行轉帳。

僅送出訂單但尚未轉帳者不會被收錄；若之後在 OB 變成已付款，下一次同步才會收錄。非轉帳付款在第一版永遠略過。

同步器依 OB 分頁規則讀取，每頁最多 100 筆。需要 `paymentReferenceId` 時才呼叫單筆 `GET /v1/user-passes/{id}`，並控制在每 Token 每小時 100 次限制內。遇到 429 或暫時性錯誤時保存游標及進度，後續接續處理。

### 6.1 分組與金額

- OB 購買 ID 是同步明細唯一鍵。
- 同一 `paymentReferenceId` 的課卡合併為一張待開立發票。
- 每張課卡成為一個商品明細；商品名稱使用 OB 課卡名稱。
- 數量依 OB 實際資料，單價使用課卡含稅金額。
- 發票總額必須等於所有商品明細合計；不一致時移至資料異常。
- 缺少付款參考編號時不自行猜測合併，移至資料異常等待人工確認。

## 7. 稅務與通知設定

第一版沿用目前綠界後台設定：

- 課稅別：應稅。
- 稅率：5%。
- 商品單價：含稅。
- 不在既有含稅金額上額外加 5%。
- 不使用載具。
- 不索取紙本發票。
- 非捐贈發票。
- 電子信箱使用 OB Email，由綠界寄送通知。

若 OB Email 缺失或格式不合法，資料移至異常，不允許開立。

## 8. 雙帳號／雙統編

兩個統編視為兩個完全獨立的綠界商店設定：

- Merchant 設定獨立。
- 開票流水號獨立。
- 發票結果與對帳資料保留實際使用的帳號。
- 操作紀錄標示切換前後帳號、操作者及時間。

管理員切換的是「新同步資料的預設開票帳號」。切換後：

- 已開立發票不受影響。
- 既有待開立資料不會被批次偷偷改帳號。
- 每筆待開立資料顯示預計帳號，管理員可在開立前逐筆切換。

帳號名稱及統編可顯示在管理頁，但 HashKey、HashIV 永不顯示。

## 9. 自訂編號與防重複

綠界自訂編號使用 `YYYYMMDDNNN`，例如 `20260926001`。流水號依實際開票帳號及日期分開計算，並在鎖定區段內原子取得。

防重複分為兩層：

- 同步層：OB 購買 ID 不得重複寫入；同一付款參考編號只形成一張有效待開立發票。
- 開票層：同一內部發票 ID 及綠界自訂編號只能成功一次。送出前重新檢查狀態，成功後保存綠界發票號碼及回傳時間。

如果送出後網路中斷、無法確定綠界是否已成功，狀態改為「結果待確認」，不得自動重送；管理員必須先查綠界再決定後續處理。

## 10. 管理操作流程

### 10.1 個人發票

資料完整的個人發票可逐筆開立，也可勾選批次開立。批次逐筆執行，單筆失敗不回滾其他成功項目。

開立前確認視窗必須顯示：

- 開票帳號／統編。
- OB 訂單或付款參考編號。
- 收件 Email。
- 商品明細與含稅總額。

### 10.2 有買方統編的發票

管理員將待開立資料切換為公司資訊發票，填寫並驗證買方統編與公司抬頭。此類資料不可加入批次開立，只能逐筆確認。

### 10.3 帳號切換

切換預設開票帳號必須顯示確認視窗，明確告知只影響之後同步的資料，不修改已開立或既有待開立資料。

## 11. 狀態

主要狀態如下：

- `PENDING`：待管理員確認。
- `INVALID`：缺欄位、金額不一致或無法安全分組。
- `ISSUING`：已取得鎖定並正在送出。
- `ISSUED`：綠界明確回傳成功。
- `FAILED`：綠界明確回傳失敗，可人工確認後重試。
- `UNCERTAIN`：送出後結果不明，禁止直接重送。
- `REFUND_REVIEW`：OB 顯示退款或相關狀態，等待人工處理。
- `REFUND_RESOLVED`：管理員已在綠界完成相應作廢／折讓，並記錄結果。

狀態轉換必須在後端驗證；前端不能自行指定任意狀態。

## 12. 退款

第一版只做偵測與追蹤：

1. 同步發現已開立訂單在 OB 出現退款相關狀態。
2. 將資料標記為 `REFUND_REVIEW`。
3. 顯示原訂單、開票帳號、發票號碼、金額及退款資訊。
4. 管理員至綠界人工完成作廢或折讓。
5. 回工作台標記結果並留下備註及操作紀錄。

系統不得自動推定應作廢或應折讓。

## 13. 失敗與併發處理

- 同步、流水號取得及開票使用 GAS `LockService`，避免排程、Ivy 與 Tako 同時執行。
- OB 429、逾時或暫時性錯誤：保存進度，顯示可重試訊息，不刪除既有資料。
- 綠界明確拒絕：保存去除機密的錯誤碼與訊息，狀態設為 `FAILED`。
- 綠界結果不確定：狀態設為 `UNCERTAIN`，禁止自動重送。
- 單筆資料錯誤不得阻擋其他同步資料或批次開立項目。
- 日誌不得保存 Token、HashKey、HashIV 或完整簽章內容。

## 14. 測試與上線門檻

### 14.1 自動測試

至少涵蓋：

- 未付款訂單被略過。
- 非轉帳付款被略過。
- 2026-09-26 00:00 邊界前後。
- 重複同步不新增資料。
- 同一付款參考編號的多課卡正確合併。
- 金額不一致、缺 Email、缺付款參考編號進入異常。
- 兩個帳號的設定與流水號完全分離。
- 個人發票可批次；有買方統編的發票不可批次。
- 批次中部分失敗不影響其他成功項目。
- 不確定結果禁止重送。
- 退款只標記待處理，不自動呼叫作廢或折讓。
- 未授權帳號無法讀取或操作發票管理功能。

### 14.2 沙箱與正式驗證

1. 使用綠界測試環境驗證請求格式、簽章、應稅 5%、含稅商品、多品項、Email 通知及買方統編資料。
2. 使用假 OB 回應及非正式資料驗證同步與防重複。
3. 驗證兩組商店設定無交叉使用。
4. 由使用者指定一筆正式測試訂單，另行取得明確允許後才進行單筆正式開票。
5. 單筆正式確認成功後，才開放批次按鈕；批次開立仍由管理員手動確認。

任何測試通過都不等於取得正式大量開票授權。

## 15. 驗收標準

- 排程或手動同步只收錄日期、付款狀態及付款方式皆符合的訂單。
- 重複同步不產生重複待開立資料。
- 同付款參考編號的多張課卡只形成一張發票及正確商品明細。
- 未經管理員操作不會送出任何正式開票請求。
- 兩個帳號可人工切換，且既有資料不被靜默改帳號。
- 發票使用應稅 5% 與含稅商品金額，不重複加稅。
- 開票成功、失敗及不確定結果能被明確區分。
- 單筆失敗不影響批次中其他項目。
- 退款不自動處理，但有完整人工追蹤資訊。
- 所有具狀態變更的操作均可追溯至操作者與時間。
- 綠界及 OB 機密資訊不出現在前端、試算表或一般日誌。
