# OB 課程關閉管理設計

日期：2026-08-23  
分支：feature/ob-course-closure-management  
狀態：待使用者審閱

## 目標

在既有教室管理後台新增「關課管理」，安全處理兩個彼此獨立的流程：

1. 依隔天預約人數，自動或手動取消未達開課門檻的 OB 課程。
2. 結束代課邀請輪次後，由管理員手動批量取消下個月仍無人領取的代課課程。

兩個流程只共用 OB API 呼叫、鎖定、稽核與錯誤處理。隔天人數關課不得順便更動請假、代課或邀請資料。

## 管理介面

管理頁新增「關課管理」分頁，顯示：

- 目前模式：手動或自動。
- 下一次檢查時間與上次執行結果。
- 22:30、23:40 各階段的候選課程。
- 每堂課套用的規則、即時預約人數、門檻與原因。
- 執行紀錄、略過原因與錯誤。
- 「立即重新檢查」、勾選、全選及批量取消。

首次正式上線固定為手動模式。手動模式仍會產生候選清單，但排程不得呼叫取消 API。管理員日後可切換成自動模式，無須重新部署；切回手動後，批次應在下一堂課執行前停止，已送出的單一 API 請求不能回復。

## 隔天低人數關課

時區固定為 Asia/Taipei。每次取消前都必須重新讀取 OB 最新預約人數，不得使用候選清單的舊值。

### 22:30

- 檢查隔天課程。
- 預約人數為 0 才取消。
- API 使用 onlyEmpty=true。

### 23:40

依下列規則判斷；若同一堂課符合多項規則，採最高開課門檻：

| 規則 | 取消人數 | 最低開課人數 |
| --- | ---: | ---: |
| 課名包含「雙人」 | 0 至 3 人 | 4 人 |
| 老師為 Jina、小美、卡拉 | 0 至 2 人 | 3 人 |
| OB 課程設定扣 2 點 | 0 至 2 人 | 3 人 |
| 其他一般課 | 0 至 1 人 | 2 人 |

老師名稱採精確比對；「雙人」由 OB 課名判斷；扣 2 點必須來自 OB API 的正式課程設定欄位，不能從課名或備註猜測。

23:40 取消已有預約的課程時，onlyEmpty=false，讓 OB 依原生流程通知與退還課卡次數或點數。若讀不到預約人數、點數設定或其他必要欄位，該堂不得自動取消，改列入人工處理。

預設取消訊息：

> 您好，您所預約 {date} {time} {course} 課程因未達開課人數因此未開班🥹謝謝

訊息可由管理後台修改。取消成功後重新同步可重建的 CourseList 並寫入紀錄，但不得修改請假、代課需求或邀請輪次；若同堂另有代課資料，仍由既有「OB 已取消」流程獨立處理。

## 排程與冪等

Apps Script 的觸發器不保證精準分鐘，因此使用固定頻率觸發器，由程式判斷 22:30 或 23:40 階段是否已到期。

- 每個「目標日期＋階段＋OB Calendar ID」只能成功一次。
- 使用 LockService 防止重複執行。
- API timeout 後先讀回狀態，再決定是否重試。
- 已取消的課程視為冪等成功，不重複通知。
- 每一堂執行前再次確認模式與最新人數。

## 代課邀請輪次與整月批量取消

既有「結束本輪邀請」改為「結束本輪／處理未領課程」：

1. 結束目前有效的老師邀請。
2. 顯示下個月所有仍未被領取的代課課程。
3. 管理員可全選或勾選後一次確認批量取消。
4. 此流程永遠為手動，不受隔天自動關課開關控制。

整月清單預期都是 0 人課程，每次 API 呼叫固定 onlyEmpty=true。若 OB 回報已有預約，該堂略過並標紅，不得強制取消。

只有 OB 取消成功後，才關閉對應的代課需求，使老師端不再看到。失敗或略過的課程保留原代課狀態，方便後續處理。這項連動只屬於整月未領課程流程，不可套用到隔天低人數關課。

## 資料與安全

Token 只存於 Script Properties，不寫入前端、程式碼或試算表。

新增兩張獨立工作表，不改既有工作表欄位與索引：

### 關課設定

- 模式。
- 特殊老師名單。
- 各規則門檻。
- 取消訊息範本。
- 失敗通知 Email。
- 各階段最後成功狀態。

### 關課紀錄

- Run ID。
- 目標日期、階段、模式。
- OB Calendar ID。
- 日期、時間、課名、老師。
- 點數設定、最新人數、套用門檻。
- 執行前後狀態、API 結果、略過或錯誤原因。
- 操作者與時間戳記。

不得清空、整張覆寫或搬移既有人工資料。CourseList 維持可重建資料的定位。

## 失敗通知

每一輪執行完成後彙整錯誤，最多寄一封摘要至 takochang68@gmail.com，不得每堂各寄一封。摘要列出失敗課程、Calendar ID、階段、最新人數、錯誤與建議人工處理方式。完全成功時不寄錯誤信。

## 自動模式啟用條件

下列條件全部通過後才能切換為自動：

- 正式 Token 已存在且唯讀連線成功。
- 預約人數、老師、課名、點數設定等必要欄位可可靠取得。
- 已驗證取消端點的退款、通知、狀態及重複呼叫行為。
- 失敗 Email 可送達。
- 觸發器、LockService、冪等與稽核紀錄正常。

任一條件不符時，後台必須阻止啟用並顯示原因。

## 驗證

### 規則測試

- 一般課、特殊老師、2 點課、雙人課的人數邊界 0、1、2、3、4。
- 多規則同時符合時採最高門檻。
- 手動模式排程只產生候選、不取消。
- 取消前人數增加時正確略過。
- 缺少必要欄位時不猜測、不取消。

### 可靠性測試

- 重複觸發、API timeout、驗證失敗、部分成功。
- 同一目標日期與階段不重複取消或通知。
- 執行中切回手動後停止後續課程。
- 失敗摘要每輪最多一封。

### 流程隔離測試

- 隔天低人數關課不修改請假、代課與邀請資料。
- 整月流程只取消 0 人未領課程。
- 整月流程僅在 OB 成功後關閉對應代課需求。

### 介面測試

- 桌面、平板與手機可查看候選、原因、狀態與結果。
- 批量操作有清楚的數量、影響範圍與一次確認。

## 發布

任何 clasp push、GAS 正式 deployment、git push、正式 OB 寫入或正式試算表建表，都需另行取得明確授權。
