# OB 調課／教室對調核對設計

日期：2026-09-02  
狀態：已確認行為，待實作計畫  
實作範圍：Sherry Aerial 現有 PWA、GAS、OB 同步及新增系統管理工作表

## 1. 目標

當管理員因老師已領代課而在 OB 直接調整兩堂課的教室或時間時，系統應辨認 A／B 或 C／D 成組對調，先產生待確認項目，再於管理員確認後同步更新代課系統的實際課程對應。

系統必須保留原始請假、邀請及領課紀錄，不得因 OB 的課程名稱、教室或 Calendar ID 對應變動而反向配錯、取消領取或重新開放已領課程。

## 2. 已確認規則

- 管理員直接編輯 OB 既有課程，不會刪除再重建。
- 可對調的教室固定為 `A ↔ B`、`C ↔ D`，不可跨組自動配對。
- 兩堂課必須在同一天；開始時間可以不同，例如 18:30 與 18:45。
- 對調通常發生在一堂代課已領取後，但也必須支援兩堂待認領、兩堂已領取，或只有一堂存在請假紀錄。
- 系統只讀取 OB 的最終狀態，不直接修改 OB。
- 自動偵測只建立候選，不立即改動代課資料；必須由冠蓉或 Tako 在管理平台確認。

## 3. 建議方案

採「同步時半自動偵測＋管理員整組確認」。

不採完全自動套用，避免一般改課、改老師或單堂移動被誤判為對調；不採純手動逐筆連結，避免管理員漏掉另一堂仍在待認領的課程。

## 4. 偵測流程

「同步 OB 課表」取得新資料後，後端在覆寫可重建的 `CourseList` 快照前，先以 Calendar ID 比較同步前後的課程：

1. 找出同一天仍存在、但課程名稱、Class ID、老師、時間或教室發生變化的 Calendar ID。
2. 將教室前綴拆出，僅在 A／B 或 C／D 配對內尋找交叉移動。
3. 以 Class ID、去除教室前綴後的課程名稱、老師與日期判斷課程身分，不以開始時間相同作必要條件。
4. 只有兩邊交叉關係足夠明確時，建立一組「疑似調課」候選。
5. 若只有單邊變化、出現三堂以上可能配對、課程身分無法唯一辨認，或疑似跨 A/B 與 C/D，候選標示為「需人工配對」，不得自行套用。
6. 已確認或已忽略的同一版本變化不得重複提醒；之後若 OB 再次改動，建立新的候選版本。

## 5. 管理平台

管理平台新增 `調課確認` 分頁及待辦數量。每組候選顯示：

- 日期。
- 兩堂課同步前的時間、教室、課名、老師與 Calendar ID。
- 兩堂課同步後的時間、教室、課名、老師與 Calendar ID。
- 受影響的代課編號、原老師、目前代課老師及狀態。
- 系統判斷理由。

操作提供：

- `確認整組調課`：一次套用兩邊對應。
- `人工配對`：候選不唯一時，由管理員指定每筆代課最後對應的 OB 課程。
- `不是調課`：保留 OB 同步結果，但不改代課對應，並記錄忽略原因。

確認畫面送出前再次讀取最新 `CourseList` 與相關請假列；若 OB 或代課狀態已再次改變，拒絕套用並要求重新同步。

## 6. 確認後的資料行為

每筆請假代課紀錄同時保留：

- 原始課程、原始時段、原始 OB Calendar ID。
- 調課後實際課程、實際開始時間、有效 OB Calendar ID。
- 調課群組 ID、調課確認時間及確認者。

各狀態處理如下：

- `待認領`：保持待認領、邀請輪次、可邀請老師及開放狀態，只更新實際時間／教室與有效 Calendar ID。
- `已領取`：保留代課老師與領取內容，只更新實際時間／教室與有效 Calendar ID。
- `兩堂皆待認領`：兩堂成組更新，各自維持原邀請狀態。
- `一堂已領、一堂待認領`：已領堂保留代課老師；待認領堂繼續開放，兩堂都顯示新的實際位置。
- `兩堂皆已領取`：兩位代課老師均保留，各自更新最終位置。
- `只有一堂存在請假紀錄`：只精準更新該代課列；另一堂保留為調課群組的佐證，不建立虛構請假紀錄。

老師端、管理端、VVIP 與 Excel 顯示以實際時間、實際教室及有效 Calendar ID 為準；歷史與異動紀錄仍可看到原始資料。

## 7. 後續核對

- OB 核對使用已確認的有效 Calendar ID，不再以原始 Calendar ID 反向判斷。
- 課程名稱核對允許成組確認後的 A／B 或 C／D 教室前綴變化，但課程種類及等級仍須一致。
- 若實際開始時間變動，更新代課的實際開始時間並重新計算延後 15／30 分鐘及下一堂占用。
- VVIP 顯示、取消狀態與容量關聯跟隨有效 Calendar ID。
- 薪資以最終有效 Calendar ID 對應 OB 結果；原始 Calendar ID 僅供追溯，不能形成第二筆薪資。
- 已確認調課若之後被 OB 改回，建立新的候選，不直接刪除舊異動紀錄。

## 8. 通知

確認調課後，僅對已領取且實際時間或教室有變化的代課老師立即推播。通知內容包含：

- 日期與課程。
- 原時間／教室。
- 新時間／教室。
- 提醒以最新安排為準。

同一老師若在同一組有多堂受影響，合併為一則通知。待認領課程不通知尚未領課的老師。推播失敗不回滾已確認的調課，但必須建立管理員可見的通知失敗紀錄。

## 9. 資料與 Sheet 安全

新增系統管理工作表 `課程調整`，保存候選版本、兩邊同步前後快照、配對結果、狀態、確認者與時間。

- `CourseList` 仍是可重建的 OB 快照。
- `請假代課紀錄` 不清空、不整張覆寫、不搬移既有欄位。
- 實作前先檢查正式表頭；若需新增欄位，只能附加於表尾。
- 確認調課時，以代課編號與 Calendar ID 尋找明確列，使用鎖定並做最小範圍更新。
- 候選建立失敗不得阻止 `CourseList` 安全同步；錯誤需留在管理待辦，不可部分套用代課對應。

## 10. 錯誤與防呆

- 找不到唯一配對：顯示人工配對，不自動更新。
- OB 同步不完整或 Calendar ID 缺失：不建立自動候選。
- 確認時資料已改變：整組拒絕並要求重新同步。
- 其中一筆代課列寫入失敗：整組回滾，不能只更新一邊。
- 對調會導致同一有效 Calendar ID 綁到兩筆非群組代課：拒絕確認。
- 跨 A/B 與 C/D：不提供自動確認。
- 已完成薪資結算的月份若發生調課：不得靜默重算，建立薪資異常待辦。

## 11. 測試與驗收

至少涵蓋：

- A／B 同時間對調。
- C／D 的 18:30 與 18:45 不同時間對調。
- 兩堂待認領、一領一待、兩堂已領及只有一堂有請假紀錄。
- 邀請輪次、代課老師與領取狀態不被重設。
- 跨組、三堂候選、單堂改課及配對不唯一時不自動套用。
- 確認後老師端、管理端、VVIP、OB 核對與薪資皆使用有效 Calendar ID。
- 時間改動後延後占用重新計算。
- 已領老師收到合併推播；未領老師不收到；推播失敗有管理待辦。
- 同時操作與中途狀態改變時整組拒絕或回滾。
- 既有人工請假、邀請、領取、薪資及 VVIP 資料未被整張覆寫。

## 12. 不包含

- 由本系統直接修改 OB 課程。
- A／C、A／D、B／C、B／D 等跨組自動配對。
- 自動替管理員決定模糊或多堂調課。
- 因調課重新通知所有邀請中老師。
